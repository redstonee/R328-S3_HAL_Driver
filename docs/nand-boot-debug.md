# R328 SPI NAND 冷启动排查

2026-11-25，MX35LF1GE4AB 的 4 MiB 镜像烧写、全量回读一致，出厂坏块标记保持，但松开 FEL 键完全断电再上电后仍进入 FEL，PH0/PH1 串口没有 boot0 输出。

## 已确认的原因与修复

旧打包脚本把连续 boot0 按每页 1 KiB 拆开，物理页后半部填 `FF`。实际 R328 ROM 按每页 **2 KiB** 加载，因而读入了间隙、遗漏后半段代码，eGON checksum 失败。读写辅助程序使用相同的物理地址回读，原先的回读 PASS 只能证明数据一致，不能证明 ROM 能启动它。

已将两个 NAND 配置的 `boot0_data_per_page` 改为 2048。32 KiB boot0 连续占 16 页。ROM 的起点扫描以 128 页为步长，所以启动区前 8 块中的 boot0 副本改放在物理块 **0、2、4、6**。应用包仍从块 8 开始，扫描至块 31；总烧写范围仍为前 4 MiB。

旧镜像必须重新构建、重新烧写。不能只更新烧写脚本，也不能只修改 JSON 后沿用旧 BIN。

## 取证依据

通过 FEL 只读保存 ROM `0x00000000–0x00007FFF`、回退 FEL 后的 128 KiB SRAM，以及 NAND 第 0 块前 64 KiB。ROM SHA256 为：

```text
187a116873f7c2b7a73a51c38920be17112db477ef7b980f16be67545dceba22
```

以下是该 ROM 的 ARM 代码地址，仅适用于此哈希，不应硬编码调用到其他版本：

| ROM 地址 | 行为 |
| --- | --- |
| `0x888` | SPI NAND 启动：先调用 `0x71C`，失败后调用 `0x57C` |
| `0x71C` | 从第 0 页尝试加载，使用 `0x7194` 参数表的两项 |
| `0x7194` | 两项参数的页数据长度均为 `2048` |
| `0x57C` | 备用起点为第 128、256、…、896 页，尝试 `0x71B4` 起的几何/读命令参数 |
| `0x3644` | 发送 `13h` 页加载、`0Fh C0h` 等待就绪、`0Bh` 读取 cache |
| `0x7D8–0x814` | 按头部长度除以每页数据长度，向 SRAM `0x20000` 连续加载 |
| `0x3CD8` | boot0 checksum 校验；失败后继续尝试，最终回到 FEL |

实读 NAND 第 0 块前 64 KiB 与旧镜像完全一致；将前 32 KiB 作为 ROM 的加载结果检查时，确实报告 `Boot block checksum mismatch`。

ROM/SRAM 原始 dump 未加入工程或 prebuilt，构建不依赖它们。单元测试独立使用 ROM 的 2 KiB 读取单位及候选起点，校验每个副本，并验证旧 1 KiB 布局会导致 checksum 错误。该测试不模拟 DDR 训练或真实 NAND 电气行为。

## 验证状态

修正后镜像已重新烧写，4,194,304 字节完整回读 PASS，块 0–31 无坏块，前后标记扫描一致。用户随后松开 FEL 键、断开全部供电再上电，确认 **应用已启动，tick 正常**。

```text

```

这是 MX35LF1GE4AB、UART0 PH0/PH1 配置的实板结果，不表示其他芯片、DDR 参数或后续修改过的应用也已验证。DDR 容量未做全地址测量，`capacity_measured` 仍为 `false`。构建清单的 `hardware_tested` 也保留为 `false`：离线打包不会自动验证新产物，已确认的具体镜像以本记录为准。读回 PASS 本身不代表冷启动成功。
